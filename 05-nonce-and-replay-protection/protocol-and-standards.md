# Nonce & Replay Protection -- Protocol & Standards

This document details the technical encoding of nonces in OID4VCI, how they appear in protocol messages, the mechanics of replay prevention, and the TxCode specification.

---

## 1. c_nonce in Protocol Messages

The `c_nonce` appears in two locations in the OID4VCI protocol: the token response and the credential response.

### Token Response

The token endpoint includes `c_nonce` when issuing an access token:

```json
{
  "access_token": "eyJhbGciOiJSUzI1NiIsInR5cCI6IkpXVCJ9...",
  "token_type": "Bearer",
  "expires_in": 300,
  "c_nonce": "tZignsnFbp223W1bq4IqDt7g0SiGx0dMM",
  "c_nonce_expires_in": 86400
}
```

| Field | Type | Description |
|-------|------|-------------|
| `c_nonce` | string | A random string generated by the issuer. Opaque to the wallet -- no structure is implied or required. |
| `c_nonce_expires_in` | integer | Validity period in seconds. After this time, the nonce is no longer accepted. |

### Credential Response

The credential endpoint may include a new `c_nonce` in its response:

```json
{
  "credential": "eyJhbGciOiJFUzI1NiIsInR5cCI6InZjK3Nk...",
  "c_nonce": "fGFF7UkhLa1eFpe0SRVB6PCEmmfjLog3M",
  "c_nonce_expires_in": 86400
}
```

This new nonce replaces the previous one. If the wallet needs to make additional credential requests (e.g., for multiple credentials in a batch offer), it must use this updated nonce. The previous nonce is invalidated.

### Nonce Rotation

Nonce rotation follows a strict consumption model:

```
Token Response:     c_nonce = "nonce_A"     <-- wallet stores this
                                                  |
Credential Request: proof contains "nonce_A"      |  wallet uses nonce_A
                                                  |
Credential Response: c_nonce = "nonce_B"    <-- wallet replaces with nonce_B
                                                  |
Next Credential Request: proof contains "nonce_B" |  wallet uses nonce_B
                                                  |
                          ... and so on
```

Each nonce is used exactly once. The issuer tracks consumed nonces to reject replays.

## 2. Nonce in the JWT Proof Payload

When the wallet constructs a proof-of-possession JWT for the credential request, the `c_nonce` is included as the `nonce` claim in the JWT payload:

```json
{
  "iss": "did:key:z6Mkh...client_id",
  "aud": "https://issuer.example.com",
  "iat": 1700000000,
  "nonce": "tZignsnFbp223W1bq4IqDt7g0SiGx0dMM"
}
```

**JWT header:**

```json
{
  "typ": "openid4vci-proof+jwt",
  "alg": "ES256",
  "jwk": {
    "kty": "EC",
    "crv": "P-256",
    "x": "...",
    "y": "..."
  }
}
```

The issuer validates the proof by:

1. Verifying the JWT signature against the public key in the `jwk` header.
2. Checking that the `nonce` claim matches the `c_nonce` issued to this session.
3. Checking that the `aud` claim matches the issuer's identifier.
4. Checking that the `iat` claim is recent (within an acceptable clock skew window).

If any of these checks fail, the credential request is rejected.

## 3. c_nonce_expires_in -- Time-Limited Validity

The `c_nonce_expires_in` field specifies the nonce's validity window in seconds. Common values:

| Value | Duration | Use Case |
|-------|----------|----------|
| 300 | 5 minutes | Tight session control, typical for interactive flows |
| 3600 | 1 hour | Allowing time for user interaction (e.g., reviewing credential details) |
| 86400 | 24 hours | Deferred flows where the user may complete issuance later |

The wallet should treat `c_nonce_expires_in` as a hard deadline. If the nonce expires before the wallet submits the credential request, the wallet must obtain a new nonce. The standard mechanism is to re-initiate the token exchange, which produces a fresh nonce.

### Issuer-Side Enforcement

The issuer must track:

- Which nonces have been issued and to which sessions.
- Whether a nonce has been consumed (used in a credential request).
- Whether a nonce has expired (based on `c_nonce_expires_in`).

A well-implemented issuer rejects requests with:

- An unknown nonce (not issued by this issuer).
- An already-consumed nonce (replay attempt).
- An expired nonce (stale request).

## 4. How Replay Attacks Work and How Nonces Prevent Them

### Attack Scenario: No Nonce

Without a nonce requirement, the following attack is possible:

```
  Legitimate Wallet              Attacker (Network MITM)              Issuer
        |                                |                              |
        |  Credential Request            |                              |
        |  { proof: <signed_jwt> }       |                              |
        |  ----------------------------> | (intercepts)                 |
        |                                |                              |
        |                                |  Replays same request        |
        |                                |  { proof: <signed_jwt> }     |
        |                                |  --------------------------> |
        |                                |                              |
        |                                |  Credential Response         |
        |                                |  { credential: <vc> }        |
        |                                |  <-------------------------- |
        |                                |                              |
```

The attacker obtains a valid credential because the proof JWT is self-contained and verifiable -- the issuer has no way to distinguish the replayed request from the original.

### Defense: Nonce Binding

With a nonce:

```
  Legitimate Wallet              Attacker                         Issuer
        |                                |                          |
        |  Token Request                 |                          |
        |  ------------------------------------------------------------->
        |  Token Response                |                          |
        |  { c_nonce: "abc123" }         |                          |
        |  <-------------------------------------------------------------
        |                                |                          |
        |  Credential Request            |                          |
        |  { proof: JWT(nonce="abc123") }|                          |
        |  ------------------------------------------------------------->
        |                                |                          |
        |  Credential Response           |                          |
        |  { credential: <vc> }          |                          |
        |  <-------------------------------------------------------------
        |                                |                          |
        |  Issuer marks "abc123" as consumed                        |
        |                                |                          |
        |                                |  Replays same request    |
        |                                |  { proof: JWT(nonce="abc123") }
        |                                |  ----------------------> |
        |                                |                          |
        |                                |  REJECTED: nonce consumed|
        |                                |  <---------------------- |
```

The replay fails because nonce `"abc123"` has already been consumed. The attacker cannot forge a proof with a new nonce because they do not possess the wallet's private key.

### Combined Defense Layers

Nonces work in concert with other mechanisms:

| Mechanism | Prevents |
|-----------|----------|
| `c_nonce` | Replay of captured credential requests |
| DPoP `jti` | Replay of captured DPoP proofs |
| DPoP key binding | Use of stolen access tokens |
| PKCE | Interception of authorization codes |
| TLS | Network-level eavesdropping |

No single mechanism provides complete protection. Defense in depth is the principle.

## 5. TxCode Specification

The TxCode (transaction code) is specified in the credential offer's grant object. It is part of the Pre-Authorized Code Grant only (it does not apply to the Authorization Code Grant, which has its own user authentication via the browser).

### TxCode Descriptor in Credential Offer

```json
{
  "grants": {
    "urn:ietf:params:oauth:grant-type:pre-authorized_code": {
      "pre-authorized_code": "SplxlOBeZQQYbYS6WxSbIA",
      "tx_code": {
        "input_mode": "numeric",
        "length": 6,
        "description": "Please enter the 6-digit code sent to your registered email"
      }
    }
  }
}
```

### TxCode Fields

| Field | Type | Required | Description |
|-------|------|----------|-------------|
| `input_mode` | string | No (default: `numeric`) | The type of input expected. Values: `numeric` (digits only) or `text` (alphanumeric). |
| `length` | integer | No | The expected length of the code. If specified, the wallet should enforce exact length. |
| `description` | string | No | Human-readable instructions for the user. May be displayed in the wallet UI. |

### TxCode in Token Request

The user-entered transaction code is included in the token request body:

```http
POST /token HTTP/1.1
Content-Type: application/x-www-form-urlencoded

grant_type=urn:ietf:params:oauth:grant-type:pre-authorized_code
&pre-authorized_code=SplxlOBeZQQYbYS6WxSbIA
&tx_code=493536
```

The `tx_code` parameter is a flat string. The issuer validates it against the code it generated and delivered out-of-band.

### TxCode Delivery

The OID4VCI specification does not mandate a specific delivery channel for the transaction code. Common channels include:

- Email to the user's registered address
- SMS to the user's registered phone number
- Display on the issuer's web portal (for same-device flows)
- Physical letter (for high-assurance scenarios)

The `description` field in the TxCode descriptor may hint at the channel, but the wallet does not need to know the channel -- it only needs to prompt the user for input.

## 6. Error Responses

### Invalid Nonce

If the credential request contains an invalid or expired nonce, the issuer returns:

```json
{
  "error": "invalid_proof",
  "error_description": "The c_nonce is invalid or has expired",
  "c_nonce": "new_nonce_value",
  "c_nonce_expires_in": 86400
}
```

The issuer may include a fresh `c_nonce` in the error response, allowing the wallet to retry without re-authenticating. This is a recovery mechanism for clock skew or minor timing issues.

### Invalid TxCode

If the transaction code is invalid, the token endpoint returns:

```json
{
  "error": "invalid_grant",
  "error_description": "The transaction code is incorrect"
}
```

The wallet should prompt the user to re-enter the code. Issuers may implement rate limiting to prevent brute-force attacks on the transaction code.
